# OQA / OQL 연구 인덱스

> 최종 확인: 2026-09-23 · 용어 갱신: 2026-09-28  
> 범위: Infocz Notion의 OQA 종합 설명서, 하위 8개 장, OQA·OQL 실무 가이드, 별도 지정된 설계·비교·회고 문서 3편  
> 주의: 이 파일은 연구용 탐색 인덱스다. 구현 사실은 항상 현재 코드가 우선하며, 아래 문서 중 설계 초안은 현행 계약으로 인용하면 안 된다.

## 한눈에 보기

OQA(Ontology Query Algebra)는 자연어 질문을 곧바로 SQL로 만들게 하지 않고, 온톨로지 어휘를 사용하는 구조화된 **OQL 질의**로 변환한 뒤 기계적으로 검증·컴파일·실행하는 계층이다. 검증된 질의 구조와 허용 매개변수를 저장한 재사용 자산은 **OQL Card**다. 오래된 자료의 `IR`은 OQL 질의 표현의 옛 이름으로, `SPS`는 저장 카드 구현의 옛 식별자로 남아 있다. 설계의 중심은 표현력을 무제한으로 여는 것이 아니라, **표현 가능한 질문은 넓게 받되 실행 가능한 구조는 닫힌 연산자 집합과 온톨로지 카탈로그로 통제하는 것**이다.

현재 흐름은 다음과 같다.

```text
자연어 질문
  -> 카탈로그·저장된 OQL Card 목록·도메인 지식으로 프롬프트 조립
  -> LLM이 OQL 질의를 작성하거나 저장된 매개변수 OQL Card를 선택
  -> 문법 디코더
  -> 온톨로지 카탈로그·타입 게이트
  -> SQL / 그래프 / 검색 평면 실행
  -> 단계 결과 결합
  -> 실행 결과만 근거로 답변 생성
```

핵심 용어는 다음과 같다.

| 용어 | 의미 |
|---|---|
| OQA | 온톨로지 어휘 위에서 동작하는 닫힌 관계대수와 그 검증·실행 체계 |
| OQL | 질의 언어. 질의 내용은 구조화된 형태로 검증·실행된다 |
| OQL Card | 검증된 질의 구조와 허용 매개변수를 저장해 재사용하는 질의 자산 |
| SPS | Semantic Prepared Statement. 과거 문서와 코드/API에서 저장된 매개변수 OQL Card를 가리키는 내부 식별자 |
| 게이트 | 문법, 카탈로그 어휘·타입, 백엔드 구성을 실행 전에 검증하는 층 |
| 카탈로그 | 온톨로지에서 자동 파생되는 타입·속성·관계·기본키 목록 |
| Tenant | 고객의 데이터와 운영 책임을 구분하는 고객 경계. 과거 자료와 코드의 `Service`에 대응 |
| Workbench | Tenant 아래의 격리 단위로, 게시본과 초안을 모두 포함한다. 과거 자료와 코드의 `World`에 대응 |
| 물질화 | 그래프·검색 결과를 파라미터 바인딩된 관계로 SQL 평면에 주입해 후속 대수를 잇는 방식 |

**표기 범위:** 2026-09-28 기준으로 질의 언어는 `OQL`, 저장된 매개변수 질의는 `OQL Card`다. 자유 질의는 `OQL 질의`라고 쓴다. 기존 Notion 페이지 제목과 역사적 설계 명칭은 원문 링크에서 그대로 둔다. 코드/API 식별자 `ir`·`ir_template`·`internal/ir` 및 `SPS`는 내부 구현을 설명할 때만 쓴다. [Axiom 연구 자료 인덱스](./research.md)의 용어 메모도 참고한다.

## 무엇이 현행이고 무엇이 과거 설계인가

문서들은 시점과 역할이 다르다. 아래 우선순위로 읽는다.

1. **현행 정본에 가장 가까움**: OQA 종합 설명서와 8개 장, OQA·OQL 실무 가이드.
2. **실측·회고 자료**: 작업 요약. 기각된 블럭 문법 v2와 현재 제품에 살아남은 개념을 구분해 준다.
3. **설계 계보 자료**: 온톨로지 쿼리 블럭 문법, SQL 대비 한눈표. 당시의 언어 경계와 대안을 이해하는 데 유용하지만 현행 OQL Card 계약이 아니다.

특히 다음을 혼동하지 않는다.

- 블럭 문법 v2 라인은 2026-07-24에 자진 기각됐다.
- 블럭 문법 v2의 `group` 재등장, `measure.over`, `formula`, `walk`, `match`를 현행 기능으로 간주하지 않는다.
- 그 라인에서 살아남은 것은 제한된 언어 경계, 평면 저작 표면, prepared statement 개념, align 계열 결합, 구 `derivation`·`ontology_query` 은퇴 방향이다.
- 현행 정본의 연산자 인벤토리는 12종이며, 검색은 대수 연산자가 아니라 별도 노드다.
- 현행 OQL 실행 계층과 LLM 저작 표면은 범위가 다르다. `follow`, `from_input`, `stages`는 실행 계층에 있으나 정본 LLM 스키마에는 아직 노출되지 않았다.

## 현재 설계의 핵심

### 닫힌 대수

모든 연산은 관계를 받아 관계를 돌려준다. 따라서 순회나 검색 결과도 관계로 돌아오기만 하면 기존의 필터·집계·정렬을 다시 적용할 수 있다. 시작점은 `source`와 `from_input`처럼 여러 개일 수 있으며, 폐쇄성은 잎의 개수가 아니라 **연산 결과가 같은 캐리어인 관계에 머무는지**에 관한 성질이다.

### 평면 저작 표면, 트리 의미론

내부 의미는 대수 트리지만 LLM에게는 SQL 절을 닮은 평면 블록을 노출한다. 디코더가 고정 순서로 트리로 접는다.

```text
source
  -> filter
  -> aggregate 또는 project
  -> order
  -> limit
  -> count / exists
```

깊은 중첩은 약한 모델과 제약 디코딩에서 실패율과 스톨을 높였다. 평면 표면은 단순한 취향이 아니라 실험 결과다. 혼합 OR은 중첩 배열 대신 조건의 `or_group` 문자열 라벨로 표현한다.

### 현행 연산자 12종

| 연산자 | 역할 |
|---|---|
| `source` | 온톨로지 타입에서 시작 |
| `from_input` | 검색 등 외부 행을 관계로 주입 |
| `filter` | 조건 적용 |
| `project` | 속성 선택 |
| `union` | `UNION ALL` 의미의 합집합 |
| `anti_join` | 키 기준 부재, 즉 “~가 없는” 질문 |
| `aggregate` | 그룹·집계 |
| `traverse` | 온톨로지 관계 1홉 순회 |
| `order` | 정렬 종단 연산 |
| `limit` | 행 제한 종단 연산 |
| `count` | 개수 종단 연산 |
| `exists` | 존재 여부 종단 연산 |

`hop`, `walk`, `pattern`, `search`는 현행 연산자가 아니다. 순회는 `traverse`, 검색은 별도 검색 노드 뒤 `from_input`, 부정은 `anti_join`으로 안내된다.

### 세 실행 평면

| 평면 | 역할 | 결합 방식 |
|---|---|---|
| PostgreSQL | 조회·필터·집계의 기본 실행 평면 | 파라미터화 SQL |
| Neo4j | 선언된 관계의 그래프 순회 | 결과를 관계로 물질화 |
| Elasticsearch / Qdrant | 키워드·유사도 검색 | 별도 검색 노드 결과를 `from_input`으로 주입 |

검색 정책의 부스트·리랭크는 대수 의미론과 다른 자산이므로 검색은 대수 밖으로 분리됐다. 폐쇄성은 검색 결과가 관계로 주입되는 지점에서 회복된다.

### 환각 방어 계층

| 층 | 책임 | 차단 대상 |
|---|---|---|
| strict 스키마 | 생성 가능한 토큰 구조를 제한 | 없는 문법·연산자 같은 구조 환각 |
| 게이트 | 카탈로그와 타입·출력 shape를 대조 | 없는 타입·속성·관계 같은 의미 환각 |
| 파라미터 바인딩 | 값을 SQL/Cypher 문자열에서 분리 | 값 주입 계열 공격 |
| 저장된 OQL Card | 구조를 사람이 고정하고 값 슬롯만 개방 | 구조·의미 환각 경로 자체 축소 |
| 지식 문서 | 도메인 용어를 값과 실행 형태로 해석 | 유효하지만 의도와 다른 잔여 오류 |

게이트는 잘못된 요청을 자동 수선하거나 조용히 폴백하지 않고 422로 거부한다. `clarify`와 중간 결과 상한 초과 거부도 “그럴듯한 오답보다 정직한 중단”이라는 같은 원칙에 속한다.

### 저장된 매개변수 OQL Card (구현명 SPS)

저장된 매개변수 OQL Card는 온톨로지에 저장되는 질의 자산이다. `SPS`는 기존 구현의 내부 이름이다.

- `ir_template`: 값 구멍을 제외하면 실행 가능한 OQL Card. 필드 이름은 현행 API 식별자다.
- `params`: `string`, `number`, `list` 타입의 파라미터 선언.
- `description`: LLM이 템플릿을 선택할 때 사용하는 필수 설명.
- 구멍 문법: `{"$param": "name"}`.
- 허용 위치: `value`, `value_number`, `value_list`, `limit_n`, `n` 같은 값 자리.
- 금지 위치: 타입 경로, 속성명 등 구조를 바꾸는 식별자 자리.

실행 시 저장 카드 이름은 정확 경로 또는 유일한 suffix로만 해소한다. 미충전·미지 파라미터, 타입 불일치, 식별자 자리 구멍, 존재하지 않는 카드 이름은 전부 결정론적 오류다. 자유 OQL 질의와 저장된 매개변수 OQL Card는 마지막에는 같은 게이트로 합류한다.

## 기능 범위

### 현재 LLM이 자동 저작하는 범위

- 조건 조회와 목록
- 개수와 존재 여부
- 그룹 집계와 상위 N
- `or_group`을 이용한 혼합 OR
- 여러 스텝 결과의 `aligns`, `diffs`, `ratios`
- 모호한 질문의 `clarify`
- 저장된 OQL Card 선택과 파라미터 채움

### 직접 OQL 질의로 가능한 추가 범위

- `follow`/`traverse` 기반 1홉 관계 순회와 후속 집계
- `from_input`을 통한 검색·외부 결과의 후속 필터·집계
- `stages` 표면의 `anti_join`

### 의도적으로 제한하거나 아직 열지 않은 범위

- 자유 조인과 임의 조인 키
- ratio/diff 결과 위 재정렬·top-N
- 스텝 결과를 다른 스텝의 입력으로 참조
- 임의 산식, 파생 컬럼, `CASE`, 문자열·날짜 가공
- 순서 의존 윈도우 함수와 고급 집계
- 다홉 순회, 최단 경로, 재귀 전개, 일반 그래프 패턴
- `intersect`, 명시적 `semi_join`
- SPS 후보 자동 수확·승격과 SPS-지식 자동생성
- OQL 질의와 OQL Card의 화면 저작

## 현재 상태와 알려진 위험

OQA 종합 설명서의 상태 장은 2026-07-27 `main`을 기준으로 한다. 이 시점에는 구 `derivation`·`ontology_query` 실행 표면 제거와 실물 질의 커버리지 검증이 완료되었다고 기록한다. 다만 이 파일을 읽는 시점의 코드를 반드시 다시 확인해야 한다.

- 구현 계층은 12개 연산자를 지원하지만 LLM 저작 표면은 더 좁다.
- `follow` 자동 저작은 약한 모델에서 아직 미성숙하다.
- 물질화 중간 입력은 기본 10,000행을 넘으면 거부한다.
- 복잡한 필터를 얹은 일부 순회 `count` 경로는 절단 결과를 셀 수 있어 조용한 부정확 가능성이 기록돼 있다.
- 검색은 최소 검색이며 기존 검색 정책 자산 전체와 동등하지 않다.
- QA는 `temperature=0`에서도 요동한다. 대표값은 단일 최고점보다 구간으로 인용한다.
- 프롬프트나 스키마의 확장은 그 자체가 회귀 벡터이므로 실행 계층 완성과 LLM 표면 노출을 분리해 검증한다.

문서가 기록한 당시의 스테일 표면에는 FE 설명 모달의 은퇴한 검색 연산자, 제거된 API를 호출하는 SDK·FE 잔존 코드, `oqa.execute` 설정 계약의 SPS 필드 누락 등이 있다. 현재 코드 조사 시 재검증할 체크리스트로 사용한다.

## 설계 계보: 블럭 문법 v2에서 남은 것

블럭 문법 v2는 `source + blocks[]`의 선형 상태기계, 2단 집계, `over`, 정적 의미 비교기, `align`을 한 언어 안에 넣으려던 별도 재설계 라인이다. 이 라인은 구현과 실험까지 진행됐지만 2026-07-24에 자진 기각됐다. 같은 기간 병행 라인이 SCM 46문항에서 먼저 42/46에서 44/46의 실측을 확보하면서 본선이 바뀌었다.

현재 설계에 남은 유산은 다음과 같다.

- 언어를 제한해 백엔드 등가성과 검증 가능성을 얻는 원칙.
- 내부 의미는 트리로 두되 LLM 저작 표면은 평면으로 만드는 원칙.
- 사람이 검증한 구조에 값만 채우는 prepared statement 개념. 현재 저장된 매개변수 OQL Card로 설명한다.
- 집계 결과를 같은 키로 맞추는 align 개념. 현재 OQL 질의의 결과 결합 계층으로 착지.
- 새 질의마다 전용 kind를 늘리는 구조의 폐기.
- `derivation`과 `ontology_query`의 은퇴 방향.

따라서 블럭 문법 v2 문서는 “다음 구현 사양”이 아니라 **현재 OQA가 왜 좁고 평평하며 저장된 매개변수 OQL Card를 지원하는지 설명하는 결정 계보**로 읽는다.

## 연구 시 확인할 질문

- 새로운 온톨로지 정의 재설계가 OQA의 **카탈로그 계약**을 바꾸는가, 아니면 LLM 지식·표면만 바꾸는가?
- 타입·속성·관계·기본키가 게이트와 프롬프트 양쪽에 동일하게 파생되는가?
- 새 연산 요구가 기존 연산 조합으로 환원되는가? 환원되지 않을 때만 연산자 후보로 다루는가?
- 새 연산의 결과가 관계로 닫히는가?
- 새 표면을 LLM에 노출하지 않고 직접 OQL 질의로 먼저 실측할 수 있는가?
- 자유 조인이나 중간 절단처럼 조용한 오답을 만들 수 있는 경로가 있는가?
- 어떤 반복 질문을 OQL Card로 저장하고 어떤 질문을 자유 OQL 질의로 둘 것인가?
- 정답성 검증은 구조 유효성, 의미 의도, 수치 동등성을 분리해 측정하는가?
- 문서의 수치가 서로 다른 모델·스키마·프롬프트 시점을 섞고 있지 않은가?
- 오래된 설계 문서의 `walk`, `match`, `over`, `formula`를 현행 기능으로 오인하고 있지 않은가?
