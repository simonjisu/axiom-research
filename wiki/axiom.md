이 문서는 FDE 교육용 Axiom 문서를 기준으로 제품의 개념과 작업 흐름을 요약한 연구용 위키다. 제품 계약이나 현재 배포 버전을 보증하는 정본은 아니다. 구현 여부·현재 동작은 코드와 현재 제품을 별도로 확인한다. 원문이 초안이고 검증되지 않았으므로 수치, 노드 목록, 도구 이름, 기능 지원 상태는 특히 시점 의존적으로 읽는다.

## 한눈에 보기

Axiom은 원천 데이터와 문서를 가져와 지식 자산으로 만들고, 그 위에 온톨로지·질의·워크플로를 구성해 업무 질문에 답하는 플랫폼이다. FDE는 고객의 질문과 판단 기준을 좁혀 최소한의 데이터·온톨로지·파이프라인·질의로 검증 가능한 흐름을 만든 다음, 실패 사례를 평가 자산으로 남기고 재사용한다.

```text
고객 업무 질문 / 기대 답
          │
          ▼
원천 연결 ── Import ──▶ Resource(관리형 데이터 자산)
                              │
             ┌────────────────┴────────────────┐
             ▼                                 ▼
      ObjectType / RelationType           Pipeline / 검색 자산
             │                                 │
      object_mapping /                 파싱·변환·색인
      relation_mapping                       │
             └────────────────┬────────────────┘
                              ▼
              OQL 질의 / OQL Card(저장된 매개변수 질의)
                              │
                     검증 게이트와 실행
                              ▼
                     결과·근거·평가
                              │
                              ▼
                   Chat / Agent / Report 등
```

## 제품 구조와 범위

### 지식 생산·지식층·지식 조합

원문은 Axiom을 세 층으로 설명한다.

| 층 | 역할 |
|---|---|
| 지식 생산 | 원천 데이터를 가져오고 파이프라인으로 가공한다. |
| 지식층 | 정의·리소스·온톨로지 등 자산을 등록하고 검색·색인한다. 온톨로지도 여기에 속한다. |
| 지식 조합 | 질문을 질의와 워크플로로 풀어 결과를 만든다. |

원문의 설명에 따르면 정의의 원본은 Core PostgreSQL이고, Neo4j·Qdrant·Elasticsearch는 그래프·벡터·어휘 검색을 위한 파생 사본이다. 사본과 원본이 다르면 원본을 기준으로 본다.

### Tenant와 Workbench

- **Tenant**는 고객의 데이터와 운영 책임을 구분하는 경계다. 멤버십, 권한, 설정, 정책, 감사 기록과 Workbench를 소유한다. 과거 자료와 구현의 `Service`는 이 경계에 대응한다.
- **Workbench**는 Tenant 아래의 격리 단위로, 게시본과 초안을 모두 포함한다. 온톨로지·리소스·파이프라인·워크플로 등을 이 안에서 관리한다. 과거 자료와 내부 코드의 `World`는 Workbench에 대응한다.
- [Axiom 라이선스 정책](https://app.notion.com/p/3e1d0c554e7e80248a5be04c9345f254)은 Tenant를 계약·데이터 경계로, Workbench를 그 아래 작업 공간으로 정의한다. [FDE 교육 초안](https://app.notion.com/p/3ded0c554e7e8172aac4fe31efb5ebcc)은 `published`와 `draft` 상태를 설명한다. 이 위키에서는 두 상태 모두 Workbench로 표기하고 게시 여부가 격리 단위를 바꾸지 않는다는 기준을 적용한다.

이 개념은 원문 기준 설명이다. 현재 구현과 권한 계약은 제품 코드에서 재확인한다.

## Resource와 데이터 흐름

원문에서 **Resource**는 “이런 표나 파일이 있다”를 등록하는 데이터 카탈로그 항목이다. 실제 객체나 관계 인스턴스 그 자체가 아니며, 타입 정의도 아니다.

- 형태 축: `table`(컬럼·행이 있는 표) 또는 `asset`(문서·이미지·오디오·비디오·아카이브·바이너리 파일 묶음).
- 위치 축: `managed`(Axiom이 보유하는 사본) 또는 `external`(고객 원천을 가리킴). 원문은 external 연결을 당시 미구현으로 표기하므로 현재 지원 상태는 별도 확인이 필요하다.
- 생산자(producer): Import, Pipeline, 사람 등 Resource를 만든 주체를 기록한다.
- Import는 외부에서 Axiom으로 들어오는 경로이자 원천의 불변 버전을 만드는 단계로 설명된다. 파이프라인은 매 실행마다 바뀔 수 있는 고객 원천을 직접 읽는 대신, 가져온 버전을 입력으로 삼아 재현성을 지킨다는 설명이다.
- 파일 Resource와 표 Resource는 변환 경계에서 서로 입력으로 표현될 수 있다. 예컨대 파일 묶음은 파일별 행과 `asset_ref`를 가진 표처럼 다룰 수 있다.

정형 데이터의 개념 연결은 다음처럼 이해한다.

```text
물리 테이블/컬럼
       ▲
       │ Resource의 위치·스키마가 실제 소스를 가리킴
       │
    Resource
       ▲
       │ object_mapping: Resource 컬럼 ↔ ObjectType 속성
       │ relation_mapping: Resource 컬럼 ↔ 관계 출발·도착 키/관계 속성
       │
ObjectType / RelationType
```

매핑은 데이터와 온톨로지의 연결 규칙이다. `object_type`은 개념의 타입·속성·기본키를 선언하고, 실제 인스턴스는 매핑으로 연결된 Resource 데이터에서 만들어진다. `relation_type`은 ObjectType 간 의미 있는 방향·기수성의 관계를 정의한다. 관계 인스턴스는 관계 Resource의 컬럼을 `relation_mapping`으로 대응시켜 해석한다. **매핑 연결선의 양방향 표현은 양방향 업무 관계를 뜻하지 않는다.** 관계 방향은 RelationType의 출발·도착 타입으로 표현된다.

## 온톨로지 자산

원문은 온톨로지를 데이터가 아니라 선언으로 설명한다. “성분은 이런 속성을 가진다” 같은 개념 정의와, 실제 인스턴스 데이터는 분리된다. 따라서 개념을 먼저 설계하고 데이터를 나중에 매핑할 수 있으며, 원천 표가 바뀌어도 의미 정의를 유지하고 매핑만 조정할 수 있다.

| 자산 | 역할 |
|---|---|
| `object_type` | 개념을 선언한다. 기본키와 속성(키·타입·설명)을 정의한다. |
| `relation_type` | 두 ObjectType 사이의 관계를 선언한다. 방향과 기수성을 가지며, 관계 자체 속성도 정의할 수 있다. |
| `object_mapping` | ObjectType의 속성을 Resource 컬럼에 연결한다. 이 연결을 통해 객체 인스턴스를 해석한다. |
| `relation_mapping` | 관계의 출발·도착 키와 관계 속성을 관계 Resource 컬럼에 연결한다. |
| `glossary` | 사용자의 표현·별칭을 타입, 관계, 속성 또는 값 집합에 연결한다. |
| `rule` | 특정 온톨로지 요소나 질의에 적용할 제약·안내를 정의한다. |

원문에 나온 ObjectType 매핑 예시는 다음과 같은 형태다. 필드와 허용값은 현재 API 계약으로 간주하지 않는다.

```json
{
  "target_object": "/object-types/성분",
  "resource": "/resources/drug_reaction",
  "bindings": [
    { "property": "name", "column": "drug_name" }
  ],
  "rows_per_identity": "many",
  "order_column": "seq_no",
  "priority": 10
}
```

원문 설명상 `rows_per_identity`는 한 식별자에 원천 행이 하나인지 여럿인지 나타내고, 여러 행이면 `order_column`으로 순서를 정한다. 한 타입에 여러 매핑이 있을 때 `priority`가 높은 매핑이 우선하며, 낮은 우선순위 매핑은 상위가 제공하지 않은 속성을 보완할 수 있다. 값이 여러 개일 때 어느 것을 남길지 정하는 `merge` 규칙은 타입 정의 쪽 업무 판단으로 설명되어, 원천 위치를 지정하는 Mapping과 구분된다.

### 모델링 원칙

1. 원천 컬럼을 그대로 ObjectType 속성으로 복사하지 않는다. 먼저 업무 질문에 답하려면 어떤 개념과 관계가 필요한지 정한다.
2. 역량 질문(competency question)을 먼저 만들고, 질문이 요구하는 타입·속성·관계만 정의한다. 예시 QA 문서는 이를 “설계 질문이 회귀 시험지가 되는” 흐름으로 설명한다.
3. 작은 질문·데이터 범위부터 end-to-end로 연결하고, 필요성을 확인하며 확장한다.
4. AI는 초안을 만들 수 있지만 타입 이름, 설명, 기본키, 속성, 관계 방향 및 의미는 FDE가 검토한다.
5. 삭제 전에 타입을 참조하는 매핑·규칙·용어가 있는지 확인한다.

## Pipeline과 정형 데이터

원문은 데이터가 이미 질문에 답할 모양이면 Pipeline이 필수는 아니라고 한다. Import된 표를 바로 매핑할 수 있고, 조인·집계·문서 파싱처럼 모양을 바꿔야 할 때 파이프라인을 둔다.

정형 실습의 흐름은 아래와 같다.

```text
PostgreSQL 연결
  → Import로 표의 불변 버전 생성
  → 필요 시 sql_transform으로 조인·집계
  → 산출 Resource 생성
  → object_mapping으로 ObjectType에 연결
  → Instance Viewer와 질문 결과로 확인
```

원문은 Pipeline 산출물을 사전에 별도 Resource로 만드는 대신 경로로 선언하는 방식, 그리고 `sql_transform`은 Axiom 관리형 저장소의 불변 버전만 읽는 방식을 설명한다. 위 세부 제약은 초안 시점의 안내이므로 실제 구축에서는 현재 `operation_catalog`와 검증 결과를 기준으로 삼는다.

## OQL 질의와 OQL Card

**OQL(Ontology Query Language)**은 질의 언어다. OQL 질의는 JSON 구조로 작성할 수 있고, 그중 구조와 허용 매개변수를 저장한 재사용 질의 자산을 **OQL Card**라고 부른다. 오래된 문서의 `IR`과 `SPS`는 관련 과거 명칭·내부 구현 식별자이며, 코드 필드 `ir`, `ir_template`은 소스 확인을 위해 그대로 표기한다. **OQA(Ontology Query Algebra)**는 검증·컴파일·실행 계층의 이름이다.

```text
질문
  → LLM이 OQL 질의를 작성하거나 저장된 매개변수 OQL Card 선택
  → 문법·온톨로지 어휘/타입·백엔드 검증
  → 결정론적 실행
  → 실행 결과를 바탕으로 답변 작성
```

핵심 원칙은 LLM이 직접 SQL이나 최종 숫자를 만들어내지 않게 하고, 닫힌 질의 구조를 작성하게 한 뒤 기계가 검증·실행하는 것이다. 유효하지 않은 타입·속성·관계, 잘못된 집계 타입, 준비되지 않은 백엔드는 실행 전 거부하는 것을 지향한다.

원문은 OQA 연산이 표를 입력받아 표를 반환하는 “닫힌 대수”와 그래프 순회 결과를 후속 질의에 이어 붙이는 방식을 설명한다. 검색은 별도 검색 노드가 수행하고, 그 결과를 질의 입력으로 넘긴다. 저장된 매개변수 OQL Card는 반복 질의의 구조를 고정하고 허용된 값만 채우게 해 자유 질의의 위험을 줄인다. 과거 설계 문서에서는 이를 SPS라고 부른다.

> 주의: 교육 문서의 연산자 수, 실행 평면, 지원 범위 설명은 버전이 고정된 API 스펙이 아니다. 상세한 현행 동작은 [OQA / OQL 연구 인덱스](./oqa.md)와 현재 `axiom-oqa-node` 구현을 함께 확인한다.

## 평가와 문제 추적

- QA 셋은 “이 온톨로지가 답할 수 있어야 하는 질문”의 목록이며, 온톨로지 설계와 시스템 회귀 평가를 잇는다.
- 질문에는 기대 답뿐 아니라 근거와 기준 SQL 등 진행자용 평가 자료를 둘 수 있다. 학습자에게는 질문만 주고 답안지는 분리하는 구성을 예시로 든다.
- 실패 시 프롬프트를 먼저 바꾸지 말고 `원천 데이터 → 매핑 → 질의 → 도구 실행 → 답변 생성` 중 어느 단계가 원인인지 좁힌다.
- 수정 전후를 같은 QA 문항으로 비교하고, 반복적으로 등장하는 질의는 검증된 매개변수 OQL Card로 저장한다.
- 자발적 신고 데이터 같은 도메인에서는 데이터가 뒷받침하지 않는 인과관계나 비율을 단정하지 않는 등 도메인 해석 한계도 답의 일부로 관리한다.

## FDE 구축 루프

원문 시놉시스가 권하는 기본 순서는 다음과 같다.

1. 고객의 반복 업무 질문, 기대 답변, 판단 근거, 최종 산출물을 정의한다.
2. 필요한 최소 데이터와 예시 QA를 정한다.
3. 고객 맥락·모호한 용어·확인할 가설을 정리한다.
4. 이미 있는 Axiom 자산을 탐색한다.
5. 필요한 데이터 처리와 온톨로지 모델을 만든다.
6. 매핑된 객체·관계를 샘플로 직접 확인한다.
7. OQA/OQL 질의와 워크플로·Agent를 연결한다.
8. QA 셋으로 정답·근거·안정성을 검증하고 실패를 추적한다.
9. 검증된 온톨로지·Pipeline·OQL Card·QA를 재사용 가능한 자산으로 남긴다.

원문이 반복해서 강조하는 역할 구분은 “AI가 만들었으니 승인”이 아니라, AI가 만든 초안을 실제 업무 의미로 확인하고 실행·실패·수정·재실행 루프를 주도하는 것이다.

### 버전 및 신뢰 범위

- 이 위키의 `v1`은 **위키 문서 버전**이며 Axiom 제품 릴리스 버전이 아니다.
- 기준 Notion 페이지의 최종 편집일은 2026-09-23이다. 페이지 자체에는 제품 semver나 대응 Git commit이 기재되어 있지 않다.
- 기준 페이지 속성은 `Draft`, 검증 메타데이터는 `unverified`다. 일부 자식 페이지는 별도 최종 편집일을 보유한다.
- 기준일 이후 바뀔 수 있는 포트, 모델, 컨테이너, 연산자 수, API 및 기능 지원 여부는 배포 설정과 코드에서 다시 확인해야 한다.
